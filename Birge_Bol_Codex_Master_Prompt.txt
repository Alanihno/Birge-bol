0. ИСХОДНАЯ КОНЦЕПЦИЯ И ГРАНИЦЫ
========================

Название: Birge Bol («будь рядом»). Позиционирование: «Найти. Понять. Видеть прогресс».

Основная проблема: родители, особенно в начале пути, не понимают, к кому обратиться, как найти действительно подходящего специалиста и как оценивать результат занятий. Реклама не равна доверию, а «сарафанное радио» доступно не всем. Продукт превращает опыт родителей и потенциального сообщества выпускниц фонда «Мама Про» в структурированные полезные рекомендации. В исходной концепции упоминается около 60 тысяч мам-выпускниц фонда: это потенциальное сообщество, НЕ действующие пользователи или подтверждённые отзывы платформы. Не выдавай демонстрационные сведения, вымышленных специалистов или цифры за настоящие.

ОСНОВНЫЕ ПОЛЬЗОВАТЕЛИ:
- Родитель-новичок: ребёнку около 2–3 лет, беспокоит речь/развитие; не знает терминов и к кому идти.
- Родитель с опытом занятий: ребёнку условно 5–8 лет; хочет понимать цели, фиксировать изменения, получать отзывы и при необходимости менять специалиста.
- Мама-наставница/выпускница фонда, добровольно помогающая другим.
- Администратор/модератор фонда, который проверяет специалистов, отзывы, словарь и рекомендательные правила.
- Специалист: на MVP может не иметь полноценного кабинета; его данные редактирует администратор. Полноценный кабинет — отдельная следующая фаза.

Обязательные базовые вкладки приложения в нижней навигации: «Найти», «Мамы», «Мой ребёнок». Дополнительные экраны: onboarding, карточка специалиста, анкета/чек-лист после занятия, объяснение терминов, настройка профиля, вход, админка. Сначала в интерфейсе новичка особенно заметны «Найти» и «Спросить мам»; дневник доступен как функция, но его активные сценарии открываются после выбора/сохранения специалиста или начала занятий. Не запрещай пользователю просматривать свой профиль ребёнка.

ВАЖНО: если в репозитории есть приложенные PDF «Birge Bol идея проекта.pdf» и «Birge Bol интерфейс MVP.pdf», изучи их и максимально точно перенеси продуктовую логику и визуальные принципы. Если файлов нет — этого ТЗ достаточно для реализации, не останавливайся. Два PDF содержат концепцию и 4 мобильных макета, а не готовую реализацию.

1. НЕПЕРЕГОВОРНЫЕ ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ
========================

1. СТРОГО НОВЫЙ ПРОЕКТ, НЕ NEXT.JS. Используй React + Vite + TypeScript. НЕ добавляй Next.js, SSR, собственный постоянно работающий Node.js/Express/NestJS-сервер, Docker, VPS или платную обязательную инфраструктуру.
2. Деплой frontend — VERCEL, Vite STATIC BUILD: npm run build -> dist. Конфиг vercel.json для SPA deep links/refresh (/specialists/:id, /admin и т.д. должны работать при прямом заходе). Не используй Cloudflare Pages в качестве основного хостинга. Убедись, что редиректы SPA не ломают статику, manifest, service worker или assets.
3. PWA: vite-plugin-pwa, manifest, app name/short_name, theme/background colors, иконки 192/512 и maskable, display standalone, start_url, offline fallback, понятный install flow (учёт различий Android/iOS), обновление service worker. Кэшируй только безопасную статику/публичные ресурсы: не кэшируй приватные данные детей и авторизованные API-ответы через публичные Workbox cache strategies.
4. UI: Tailwind CSS + shadcn/ui (или эквивалентные доступные исходники компонентов), React Router, TanStack Query, React Hook Form + Zod, Lucide icons. Текущие стабильные совместимые версии выбирай по доступной среде, без бесполезных зависимостей.
5. BaaS: Supabase Free (PostgreSQL, Auth, RLS, Storage, Edge Functions). Никакого обязательного оплачиваемого сервиса. Конфигурация из .env.local, шаблон .env.example. В клиенте допустим ТОЛЬКО publishable/anon key, но НИКОГДА service_role, Gemini API key, Telegram bot token и другие серверные секреты. Если Supabase не подключён, обеспечь безопасный явный DEMO MODE с локальными тестовыми данными, чтобы UI не был пустым и сценарии можно было показать; деморежим должен быть явно помечен и не имитировать реальные подтверждения/записи.
6. Gemini API — только как ОПЦИОНАЛЬНЫЙ серверный провайдер через Supabase Edge Function и секрет GEMINI_API_KEY; ключ пользователь передаст позже. Сейчас не требуй его и не блокируй сборку. Все основные функции должны иметь детерминированный fallback без ИИ (проверенный словарь, шаблоны текстов, правила). Не вызывать Gemini прямо из браузера. Не обещать безлимитную бесплатность внешнего API: обеспечь rate limiting, ограничение размера запросов, обработку квот/ошибок, возможность полностью отключить ИИ.
7. Telegram Bot API — опционально, только через серверный webhook/Edge Function; секрет токена никогда не в React. Без токена показывай рабочую in-app demo модель вопросов и ответов с маркировкой, а не фальшивую отправку в Telegram.
8. Карта — Leaflet + OpenStreetMap с аккуратной атрибуцией и соблюдением правил tile provider. Для MVP основной режим — список, карта — переключаемый вид; без обязательных платных Google Maps API. При отсутствии координат не придумывай геолокацию/расстояние. Адрес и маршрут открывай внешней картой только при наличии реального адреса/координат. При масштабировании обозначь необходимость другого допустимого tile provider.
9. Сначала поддержи русский интерфейс, подготовь полноценную инфраструктуру i18n для казахского, а основные пользовательские строки реализуй и на казахском, если это укладывается без ущерба ключевому MVP. Не оставляй вперемешку непереведённые интерфейсные заголовки; учитывай длину строк.
10. Мобильный UX имеет приоритет, desktop тоже должен быть полноценным (не растянутый мобильный экран). Доступность WCAG насколько практически возможно: семантические элементы, keyboard navigation, focus, aria-labels, контраст, reduced motion, label/input linkage, читаемые размеры.
11. Без запрещённой подмены реальности: никаких «проверенных» отзывов, мест/записей, реальных результатов, партнёрства, диагноза, свободных слотов или уведомлений, если нет подтверждения из backend. Все примеры помечены «Демоданные».
12. Никаких hardcoded API-ключей, никаких оплачиваемых image APIs. Допустимы собственные SVG/иллюстрации, CSS-графика, Lucide, аккуратно лицензированные бесплатные фотографии с документированным источником. Не используй фотографии реальных детей с особыми потребностями без разрешения. В UI изображения/иллюстрации должны помогать понять интерфейс, а не перегружать его. Предпочти авторские абстрактные иллюстрации/аватары вместо стоковых медицинских фото.
13. НИКОГДА не запускай на реальных персональных данных детей без отдельной юридической, privacy и security проверки. Законодательство Республики Казахстан, включая вопросы персональных данных, чувствительных сведений, трансграничной передачи и локализации/размещения баз, должно быть проверено ответственными специалистами до production-пилота. Supabase-хостинг за рубежом не считай автоматически законным вариантом. В MVP используй вымышленные профили, демонстрационное аудио и синтетические отзывы.

2. ДИЗАЙН-СИСТЕМА И КАЧЕСТВО UI
========================

Визуальное направление — максимально качественный современный consumer health/social-impact продукт: спокойный, доброжелательный, профессиональный, доступный и эмоционально безопасный. НЕ выглядит как больничная CRM, банальный дашборд SaaS, детский мультфильм или шаблонный AI-лендинг.

Ориентир исходного UI: тёплый почти белый/кремовый фон, мягкий фиолетовый как основной брендовый цвет, светло-лавандовые блоки, спокойные коралловые CTA, зелёные статусы, графитовый текст, большие радиусы карточек, воздушные отступы, небольшие простые круглые аватары, понятные формы и нижняя навигация. Реализуй в токенах дизайн-системы с доступным контрастом; аккуратно улучшай эстетику оригинала, не копируй механически плохие решения.

Требуется:
- Профессиональная типографика с хорошей кириллицей, единая шкала текста, максимальная читаемость на 320–430 px.
- На телефоне bottom tabs, аккуратные safe-area insets, липкий нижний CTA только где уместно, без перекрытия контента. На desktop — удобная навигация и центрированные контентные колонки, фильтры/сайдбар и лист/карта при подходящей ширине.
- Skeleton states, empty states, loading, error, retry, success; мягкие micro-interactions без тяжёлой анимации.
- Чёткий приоритет действий на каждом экране, 1 главный CTA, небольшое число второстепенных.
- Не показывать 20 фильтров одновременно — важные фильтры чипами, остальные в sheet/dialog.
- Понятные объяснения без жаргона: «Зачем этот специалист?», «Что взять на приём?», «Какие вопросы задать?», «Что будет дальше?».
- Изображения: для onboarding и пустых состояний — дружелюбные оригинальные SVG/геометрические иллюстрации; у специалистов — аватар с инициалами или загруженное подтверждённое фото; без выдуманных фотографий людей.
- Не захламлять экран баннерами, декоративными графиками, случайными фото или большим количеством цветов.
- Сильные UX детали: прогресс заполнения анкеты, живые счётчики фильтрации, понятные сообщения доверия, теги «онлайн», «от 15 000 ₸», «подтверждённый отзыв» только при правдивых данных.
- Все интерактивные элементы реально работают: сортировка, фильтры, кнопки назад, табы, модальные окна, формы, clear/reset, сохранение, поиск, переходы.
- Не используйте lorem ipsum, бессмысленные KPI, фейковые графики, пустые разделы с «coming soon» в основной навигации.

3. МОДУЛЬ A — ПЕРВЫЙ ВХОД, ПРОФИЛИ И ОНБОРДИНГ
========================

Маршруты: /, /welcome, /onboarding, /auth, /profile, /settings (можно адаптировать названия).

Открытие: краткое объяснение пользы, CTA «Начать поиск», ссылка «Как это работает», понятное объяснение, что это не диагностика. Не заставляй создавать аккаунт для первой ознакомительной анкеты и просмотра публичного каталога. Для сохранения профиля, отзывов, дневника, вопросов и личных функций нужен вход.

Анкета в 3–5 коротких шагов с сохранением черновика локально (без утечки) и прогрессом:
1) возрастная группа / месяц и год рождения (без необязательной точной даты),
2) город и район (выбор из справочника, без принудительной геолокации),
3) что беспокоит (речь, коммуникация, поведение, обучение, письмо, внимание, другое; множественный выбор),
4) есть ли заключение/обращались ли к специалистам (без обязательной загрузки документов),
5) желаемая цена, допустимая дистанция и онлайн/очно.

Не требуй имя ребёнка или диагноз для поиска; минимизируй данные. Поддержи несколько профилей детей у одного родителя; переключатель активного профиля. Для логина MVP достаточно безопасной авторизации Supabase Auth по email (OTP/magic link или password по выбранной реализации); SMS платный провайдер не использовать. Реализуй корректное восстановление сессии, logout, protected routes, onboarding skip, согласие на обработку данных (в demo не собираем реальные чувствительные данные) и понятные privacy notices.

Схема: profiles, children, child_concerns, consents или аналогичные нормализованные таблицы. Роли parent, mentor, moderator, admin — но не давай назначать admin/mentor самому себе через client SDK. Продумай parent_id, ownership policies, запрет просмотра чужого ребёнка.

Критерий готовности: незалогиненный пользователь проходит анкету и видит деморезультат; вошедший пользователь может сохранить/изменить профиль, данные не смешиваются между аккаунтами.

4. МОДУЛЬ B — ПОДСКАЗКИ «КОГО РАССМОТРЕТЬ»
========================

После анкеты показывай короткий блок «С чего можно начать», с 1–3 шагами, причиной и ожидаемым следующим действием. Не диагностируй. Исходный демонстрационный сценарий: ребёнок 3 лет почти не говорит; возможные темы для обсуждения с профильными специалистами — оценка речи, проверка слуха, получение информации о ПМПК. Это иллюстрация, не универсальное медицинское назначение.

Технически: rules engine — versioned, reviewable if/then правила в PostgreSQL (recommendation_rules, rule_versions) или чистом типизированном модуле с возможностью последующей миграции в БД. Условия: возрастная группа, concern tags, наличие заключения, город, онлайн/очно. Предусмотри приоритеты, конфликты, fallback «нужна консультация квалифицированного специалиста», безопасные тексты. Правила не должны редактироваться произвольным пользователем. Тексты и правила требуют проверки специалистами фонда; до проверки помечай их как пример.

Не используй Gemini для принятия клинических решений. Gemini, если подключён, может только упрощать язык уже готового проверенного объяснения. Ссылки на каталог по рекомендованной специализации должны открывать реальный фильтр. Добавь тесты на правила и граничные условия.

5. МОДУЛЬ C — ПОИСК СПЕЦИАЛИСТОВ
========================

Главный маршрут /find. Вверху — компактный профиль активного ребёнка и «Вам могут подойти»; ниже поисковая строка «Логопед, специальный педагог...», фильтры и список.

Реализуй:
- Поиск по имени, специализации, услугам; нормализацию запроса.
- Фильтры: город, район, специализация, проблема/запрос ребёнка, возрастная группа, очно/онлайн, диапазон цен, возможная бесплатная помощь через ПМПК (только по подтверждённым условиям), расстояние при наличии координат, доступность.
- Сортировка: релевантность, расстояние, стоимость, показатели контакта с детьми похожих профилей (с оговорками по размеру выборки).
- Чипы активных фильтров и сброс; debounce поискового запроса; pagination или «показать ещё», состояния пустого результата.
- Переключатель «Список / Карта». Карточка показывает имя, специализацию, район, очно/онлайн, цену, статус доступности только при достоверных данных, число проверенных отзывов, показатель контакта только при достаточном количестве оценок. Не показывай несуществующий «1,2 км» если координат нет.
- Переход на /specialists/:id, сохранение в избранное, контакты/направления.

Данные: specialists, specializations, specialist_services, service_age_ranges, locations, specialist_photos, verified_credentials, reviews. Используй PostgreSQL индексирование, limit, RLS. Публичный каталог должен отдавать только разрешённые поля опубликованных карточек. Контактные данные специалиста показывай только с его согласия. Геопоиск при необходимости через PostGIS, но не усложняй demo, если координаты недоступны.

Демобаза: 20–30 явно ВЫМЫШЛЕННЫХ специалистов в нескольких районах одного пилотного города с разнообразными специализациями/ценами/форматами; синтетические тестовые отзывы, отдельная маркировка «Демо». Данные не должны выглядеть как проверенная реальная сеть.

========================
6. МОДУЛЬ D — ПОДРОБНАЯ КАРТОЧКА СПЕЦИАЛИСТА
========================

Как во втором макете: имя и квалификация, стаж и формат, район, цена, рейтинг КОНТАКТА (не медицинская эффективность), количество подходящих подтверждённых случаев, описание «Что делает специалист и чего можно ожидать», примерные этапы работы, «Что взять на первый приём», подготовленные вопросы врачу, отзывы родителей детей похожего возраста/запроса, действие «Записаться» и «Маршрут».

Каждый специалист может вести несколько услуг; этапы не универсальны и должны редактироваться верифицированным админом. Не обещай неизбежный терапевтический результат. Скрывай рейтинг при недостатке данных или показывай «Пока мало оценок».

«Дети как ваш»: объяснимое matching по возрастной группе и concern tags, анонимные обобщённые отзывы. Рейтинг считать из структурированных подтверждённых ответов, учитывать размер выборки для сортировки, отделить оценку контакта от результата. Никакого автоматического раскрытия имени ребёнка, редкого диагноза, даты рождения или других идентификаторов.

CTA записи в MVP: реальный контакт/внешняя запись, если они добавлены и валидны; иначе «Уточнить способ записи» и честное сообщение. Не имитируй подтверждённую бронь. «Маршрут» только по реальному адресу. Добавь функцию сохранить специалиста себе и отметить факт записи/посещения вручную как самостоятельное заявление пользователя (не подтверждённый факт).

9. МОДУЛЬ G — ПОСЛЕ ЗАНЯТИЯ: ЧЕК-ЛИСТ И ОТЗЫВ

1) «Ребёнок пошёл на контакт?» шкала 1–5;
2) «Специалист подстроился под ребёнка?» Да/Частично/Нет;
3) «Объяснили, что было на занятии?» Да/Нет;
4) «Есть понятная цель на месяц?» Да/Нет;
5) пятый простой вопрос о комфорте/понятности следующих шагов (сформулировать нейтрально).

Сохраняй структурированные ответы в session_feedback. Отдельно спрашивай разрешение на создание отзыва. Автоматически формируй РЕДАКТИРУЕМЫЙ черновик из фактических ответов: deterministic template fallback обязателен. Опциональный Gemini генератор через Edge Function: не выдумывает эффекты, диагнозы, достижения, длительность занятий или чужие слова, не изменяет смысл; ограничить промпт, вывод и токены. 14. БАЗА ДАННЫХ И ЗАЩИТА
========================

Создай реальные миграции SQL в supabase/migrations, типы TS, seeds для вымышленных данных и документацию к схеме. При необходимости используй следующие сущности, оптимизируя без избыточности:
profiles, user_roles, children, child_concerns, consent_records, cities, districts, specializations, specialists, specialist_services, service_age_ranges, specialist_locations, recommendation_rules, rule_versions, medical_terms, favorites, appointments (только ручные/пилотные статусы на MVP), waitlist, session_feedback, reviews, review_reports, mentors, questions, answers, child_goals, progress_entries, progress_recordings (demo first), notifications, moderation_actions, audit_logs.

Требования:
- UUID primary keys, foreign keys, unique constraints, CHECK constraints для статусов/оценок, created_at/updated_at, индексы для фильтрации.
- Везде RLS, принцип least privilege. Анонимный доступ только к разрешённому публичному каталогу и проверенным опубликованным текстам; личные дети/отзывы-черновики/чаты недоступны другим семьям.
- Проверяй ownership по auth.uid(), роли назначаются доверенным сервером, не клиентом. Запрет mass assignment и privilege escalation.
- Клиентский SUPABASE_ANON_KEY не секрет, защита строится на RLS; service role остаётся только на сервере.
- Edge Function: проверка JWT при пользовательском вызове, проверка webhook authenticity при Telegram, серверная валидация Zod/эквивалент, CORS с ограничением origin где применимо, rate limiting, структурированные ошибки, no logging private text/token.
- Безопасные URL для внешней записи (нельзя javascript:), защита от XSS, безопасный вывод пользовательских текстов, ограничение длины сообщений и отзывов.
- Публикация отзывов через модерацию; не скрывать отрицательные отзывы необоснованно, но не позволять травлю и клевету.
- Пользователь может отозвать согласие, удалить свой вопрос, отзыв и профиль по применимым правилам. Для полного удаления аккаунта — защищённый процесс; где не сделано, честно документировать.
- Не собирать ИИН, точные адреса ребёнка, сканы заключений, настоящий детский голос в live MVP.
- Законы РК не имитировать: составь отдельный SECURITY_AND_COMPLIANCE.md с реальными пунктами проверки перед пилотом, но не пиши «полностью соответствует закону» без юридической оценки.
